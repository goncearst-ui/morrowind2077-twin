# Порядок операций и формул для побитовой сверки C++ с двойником (задача 23d)

Статус: справочник для будущей задачи «ядро на C++» (не входит в 23). Двойник; Creation Kit и SFSE не затрагиваются. Метки [предл] = предложение агента, Стан не утверждал. Дата замеров: 2026-10-28, Python 3.13.18.

Простыми словами: чтобы C++-ядро выдавало те же числа до последнего бита, оно обязано считать в том же порядке и записывать числа тем же способом. Ниже перечень мест, где это не очевидно. Всё, что ниже, проверено на двойнике или явно помечено «не проверено».

## 1. Правило общего вида
Источник истины для формул — сам код `twin/model.py` и модулей рядом. C++-версия переписывает каждое выражение буквально: те же скобки, тот же порядок слева направо, те же промежуточные переменные. Алгебраические упрощения (вынести общий множитель, заменить деление умножением на обратное, сгруппировать слагаемые иначе) запрещены: в числах с плавающей точкой `(a + b) + c` и `a + (b + c)` могут отличаться в последнем бите.

## 2. Таблица мест, где легко разойтись

| № | Что | Как в двойнике | Что обязано делать C++ | Проверено |
|---|---|---|---|---|
| 1 | Тип числа | дробные — double (IEEE 754, 64 бита), целые — Python int (в мире значения малы, влезают в int64) | double и int64; целое в дробное переводится точно (значения < 2^53) | да (чтением кода) |
| 2 | Слияние умножения со сложением (FMA) | Python не сливает | компилятор: GCC/Clang `-ffp-contract=off`; MSVC: режим без слияния (точное имя флага проверить при сборке на HP OMEN); без `-ffast-math`, без `/fp:fast`; только SSE2/AVX-регистры double, без x87 | не проверено (C++ нет) |
| 3 | Порядок в выражении | слева направо, как написано; пример сумм: `(base + (manpower + wounded) * per_head_cost) * archetype_cost_mult` | та же скобочная структура | да |
| 4 | Суммирование | двойник суммирует простым циклом слева направо: функция `fsum` (twin/arith.py), встроенной `sum` в модельных модулях нет (задача 23e, проверка SM1). | 5 | Округление журнала `round(x, 4)` | точное, по десятичной записи двойного числа (`round(2.00005, 4) == 2.0`, `round(0.00015, 4) == 0.0001`) | не `floor(x*1e4+0.5)/1e4`; нужна точная десятичная запись (например `snprintf("%.4f")` + `strtod`, проверить на целевом компиляторе) | да (поведение Python), C++ не проверялся |
| 6 | Запись числа в снимок | `float.hex()`: ровно 13 шестнадцатеричных цифр у обычных чисел (`0x1.8000000000000p+0`), ноль — `0x0.0p+0`, минус ноль — `-0x0.0p+0`, субнормальные — `0x0.0000000000001p-1022` | собственный форматтер, не `%a` (у `%a` цифры сокращаются: `0x1.8p+0`) | да (Python) |
| 7 | Целочисленное деление и остаток | `//` и `%` округляют вниз: `-7 // 2 == -4`, `-7 % 2 == 1`; `int(-3.5) == -3` (к нулю); `floor`/`ceil` из `math` | в C++ `/` и `%` усекают к нулю; для отрицательных значений нужны свои функции | да (Python) |
| 8 | `min`/`max` | при равенстве возвращают первый аргумент; NaN в мире не допускается | тот же порядок аргументов; NaN считать нарушением инварианта | да (чтением кода) |
| 9 | Порядок обхода словарей | порядок вставки (фракции, регионы, объекты, пары войн и обид); там, где код пишет `sorted(...)`, обход по возрастанию строк | порядок вставки хранить явно; `sorted` по строкам = сравнение кодовых точек Unicode; для UTF-8 это побайтовое сравнение | да: в ref_small смена порядка обхода фракций, регионов и объектов на обратный не меняет ни одно число (только порядок записей в `events` и в списке объектов), но порядок остаётся частью снимка |

## 3. Что значит «побитово» в этой задаче
Сверка идёт по золотым файлам `tests/golden/` (см. `tests/golden/MANIFEST.json`): снимки состояния на тиках 0, 100, 500, 1000 и два журнала в CSV. В CSV каждая ячейка имеет тип (`i:` целое, `f:` дробное в `float.hex()`, `s:` строка, `b:` да/нет, `n:` пусто); поэтому сравнение идёт по тексту, без допусков. Строки подробного журнала содержат уже округлённые до 4 знаков числа (`round(x, 4)`, пункт 5), а снимки содержат точные значения: расхождение в последнем бите C++ увидит в снимке, даже если журнал совпал.

## 4. Что не проверено (нужно на стадии C++)
- Слияние умножения со сложением: проверяется только сборкой и сравнением (пункт 2).
- Точное округление и форматтер `float.hex` на целевом компиляторе (пункты 5, 6).
- Совпадение результата на других машинах и других сборках Python: золотые файлы снимались в одном окружении (Python 3.13.18). После 23e сумма от версии Python не зависит.
- Миры других размеров: для полного масштаба (1000 планет) побитовая сверка не предполагается, там проверяются инварианты ядра [решение Стана 2026-10-28].
