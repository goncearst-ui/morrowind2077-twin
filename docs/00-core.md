# 00 — Ядро: тик, состояние, оси

*Источник: §13, §15.1, §15.5. Ревизия «ростер». Ревизия «системный аудит» (2026-08-16). Ревизия «enRAGE» (2026-10-19). Зависимости: нет. От ядра зависят все модули.*

*Сценарий документа: **в CE2 не появилось ничего принципиально нового.** Базлайн — известное поведение Skyrim/FO4. Всё сверх него считается отсутствующим до проверки в CK.*

---

## Что делает ядро

Три вещи и ни одной больше:

1. **Часы** — единственный 24-часовой тик на весь мод, с фиксированным порядком фаз
2. **Реестр состояния** — все Global'ы объявлены здесь, модули их только пишут и читают
3. **Оси** — R/P/C/M считаются здесь

Плюс инструмент разработчика: **холостой стенд** (§15.5) и его внеигровой двойник (модуль 11). **С ревизии enRAGE — плюс схема снимка состояния (ниже), общая для игры и двойника.**

Ядро не содержит ни одного NPC, ни одного Package, ни одного диалога. Это принципиально — оно должно собираться и тестироваться в пустом пространстве.

---

## Реестр — на фракцию, не на мод

**Добавлено аудитом.** Всё, что ниже, описывает набор Global'ов **одной фракции**. С модулями 08/13/15/17 фракций становится две-три, и каждая несёт свой экземпляр реестра. Правила:

- Префикс инстанцирует реестр: `TF1_Supply`, `TF2_Supply`, … (конвенция имён фиксируется до заморозки).
- Кросс-фракционное чтение — только через property-ссылку на тик-квест чужой фракции (приём зафиксирован в 17). Общего реестра «всех активных фракций» в прототипе нет и не строится.
- Всё общемодовое (реестр активов 15, диплом-массивы 08, `TF_PlanetHegemon` 14, **настройки `TF_Cfg_*`**) существует в одном экземпляре и в префиксную схему не входит.

Новых фаз и обходов нет. **Калибровочные константы ревизии** (`ASSAULT_LOSS_CAP`, `AssaultArmoryMin`, `DesertionCapPerTick`, `ShockEventCap`, `DepotLossRate`, `VendettaTicksMax`) — properties скриптов, не Global'ы, и в реестр не входят.

### Канонический enum архетипов — зафиксирован аудитом

Прототипная нумерация — каноническая и не совпадает с легаси-словарём концепт-дока (там Дрейфующие = 9, Культисты = 3). Легаси-номера не используются нигде:

```
0 Хранители   1 Хищники   2 Контролёры   3 Дрейфующие
4 Культисты   5 Regime    6+ — резерв второй очереди
```

После первого релиза enum замораживается вместе с реестром.

### Новый класс: кэш ростера

| Класс | Где истина | Когда меняется | Пример |
|---|---|---|---|
| хранимое | в Global | пишет модуль-владелец | `TF_Supply` |
| производное | нигде, считается | фаза 4 каждого тика | `R`, `P` |
| **публикуемая производная** | **считается и публикуется в Global** | **своя фаза, модуль-вычислитель** | **`TF_DaysSupply`** |
| **кэш ростера** | **в ростере** | **дельтой на событии** | **`TF_Manpower`** |
| **настройка** *(enRAGE)* | **в Global** | **только по действию игрока через предмет-пульт** | **`TF_Cfg_EventRate`** |

> **Кэш ростера — значение, истина о котором лежит в ростере (03), а в Global хранится копия, правящаяся дельтой.**

**Публикуемая производная — класс, добавленный аудитом.** Причина техническая и жёсткая: Condition'ы пакетов, диалогов и enable-parent'ов умеют дёшево читать только Global (`GetGlobalValue`) — они не вызывают функции Papyrus. Всё производное, что потребляется Condition'ами (ступень снаряжения 01, наборы сцен 12/12a, чатер 09), обязано публиковаться в Global в момент пересчёта. Это не источник истины, а зеркало: пишет его ровно один модуль в ровно одной фазе, читают все. До этого класса `DaysOfSupply` «не хранился нигде» — и одновременно читался Condition'ами в трёх модулях, что было невозможно. `pendingArch` был приватной переменной скрипта 07 — и одновременно читался модулями 09 и 12. Оба противоречия закрыты публикацией.

**Настройка — класс, добавленный ревизией «enRAGE».** Отличается от хранимого тем, что симуляция её никогда не пишет: только игрок, только через интерфейс настроек (11). Отличается от константы тем, что меняется в рантайме. Аудит G4 по логу: любая запись в `TF_Cfg_*` с `module` ≠ «настройки» — дефект.

Правило работы с кэшем: **никогда не пересчитывать обходом ростера.** Только `+=` / `-=` в момент, когда человек меняет ведро. Полный пересчёт существует ровно в двух местах: как инвариант на двойнике и как отладочная консольная команда. На тике его нет.

`TF_Manpower` перестал быть хранимой переменной — это правка, а не переименование. Всякий код, который его *задаёт*, кроме 03, — дефект контракта, ловится на G4.

### Производные — считаются в фазе 4

```
Расход       = КоштБазы + TF_Manpower × Ставка × МножительУклада
DaysOfSupply = TF_Supply ÷ Расход          → публикуется в TF_DaysSupply

R = f(DaysOfSupply, TF_Manpower)               ; 0–100
P = f(TF_PersonnelShock, TF_TerritorialShock)  ; 0–100
```

`DaysOfSupply` — центральная производная всего мода. Её читают четыре модуля: 07 (ось R), 06 (голод), 01 (ступень снаряжения), 09 (чатер). Из Papyrus — вычислением; из Condition'ов — через зеркало `TF_DaysSupply`.

Правило: ни один модуль не создаёт свой параллельный Global для того, что уже есть в реестре.

### Правило единственного писателя — уточнено аудитом

У каждого Global ровно один модуль-владелец. Событийные входы чужих модулей идут **через функции владельца**, а не прямой записью:

| Кто хочет изменить | Что вызывает | Владелец |
|---|---|---|
| 03 (гибель), 06 (дезертирство), 13 (штурм) | `Shock.AddPersonnel(N, вес)` | 04 |
| 06 (сдача актива, удар по складу), 13 (захват) | `Shock.AddTerritorial(N)` | 04 |
| 13 (трофей) | `Economy.TransferTrophy(победитель, побеждённый)` | 06 |
| **сцена, 13 (захват площадки со складом), 19** *(enRAGE)* | **`Economy.DepotStrike(тяжесть)`** | **06** |
| **06 (переезд склада), 13, 19** *(enRAGE)* | **`Knowledge.Reveal(тип)` / `Knowledge.Forget(тип)`** | **09** |
| 05 (смерть вожака) | `Evolution.ApplySuccession(newArch)` | 07 |
| **05 (смерть вожака)** *(enRAGE)* | **`Intent.ApplySuccession(профиль, причина)`** | **16** |
| 16 (провал цели) | прямая запись `TF_Morale` — 16 внесён в писатели реестра | 16 |

Так аудит G4 по логу остаётся тривиальным: `module` ≠ владелец — дефект без исключений.

## Гранулярность симуляции — конституционное правило

Правило того же класса, что §1 и «один модуль в CK одновременно» (11).

> **Симулируй на той гранулярности, на которой игрок способен заметить разницу. На ступень мельче — это уже не мир, а бухгалтерия.**

Операционально — различение **симуляции происхождения** и **вывода происхождения**.

Пример, на котором правило было сформулировано. Желание: «NPC носит ствол не потому, что я вписал его в редакторе, а потому что клан его где-то добыл».

| Что | Наблюдаемо игроком | Цена |
|---|---|---|
| у бойца снаряжение лучше, чем месяц назад | **да** | одно число |
| стало лучше после удачного налёта | **да**, если видел налёт или слух | то же число |
| это *тот самый* ствол из *того самого* налёта | **нет** — нечем показать | пер-предметный учёт |

### Второй пункт: личность ≠ предмет

**Добавлено ревизией «ростер».** Формулировка выше в исходном виде провоцировала неверное обобщение — будто правило запрещает любую индивидуализацию. Оно запрещает индивидуализацию **без наблюдаемого следствия**, и человек этот тест проходит там, где предмет проваливает:

| Вопрос правила | Серийный номер ствола | Человек с именем и трейтом |
|---|---|---|
| что изменится в кадре? | ничего | он есть или его нет; он на другом месте; он теперь вожак |
| свяжет ли игрок со своим действием? | нет | да, если знал его |
| дешевле вывести, чем посчитать? | да, вывести | **выводить нечего — судьба не производная** |

> **Гранулярность личности не равна гранулярности предмета.** Правило требует наблюдаемого следствия, а не малого числа сущностей.

Отсюда прямое следствие: у **всех** людей в ростере есть трейты (03). Дорого не число людей, а число **тикающих переменных** на человека — и вот их у рядового ноль.

### Третий пункт: цена — это тик, а не хранение

> **Тик работает за O(фракций). Обход ростера в фазе тика запрещён.**

Триста строк в хранении не стоят ничего. Триста итераций Papyrus каждые игровые сутки убивают проект. Все аггрегаты по людям — кэши, правящиеся дельтой на событии (03).

**Сверка с enRAGE (ревизия 2026-10-19).** RDR2-мод *enRAGE* хранит у каждого встреченного NPC собственный разум — потребности, стресс, память, цели — и обновляет «жизнь» мира каждый игровой час. Он может себе это позволить: ядро — внешний C#, состояние — JSON вне сейва. Это **не опровергает** третий пункт, а показывает, чего он стоит: правило — следствие ванильного Papyrus, а не вкуса. Если когда-нибудь часть симуляции переедет во внешний плагин (11, спайк SFSE), пункт пересматривается только для холодного слоя; горячий остаётся O(фракций).

### Прецедент, закрывающий спор о легибельности

Radiant AI в Oblivion изначально был агентной симуляцией потребностей. Систему урезали, и **задокументированная причина — не производительность и не хаос**, а понятность: Пит Хайнс (PC Zone, март 2006) объяснял, что кражи NPC у игрока пришлось убрать, потому что иначе игрок решил бы, что предметы пропали из-за бага.

Симуляция работала. Игрок не смог её прочитать.

*Оговорка: расхожая история «NPC перебили друг друга» — во многом фольклор. Урезание ради понятности подтверждено, резня — нет.*

**Симметричное наблюдение, добавленное ревизией.** Тот же довод часто приводят про A-Life в STALKER — но там был канал, который работал: новостная лента КПК. Симуляция была невидима **в мире**, а не в тексте. Отсюда — сводка как легитимный канал в 09, с ограничением: она объясняет то, что игрок мог заметить, а не заменяет замечание.

### Как правило применяется на практике

Перед добавлением любого слоя — три вопроса подряд:

1. **Заметность.** Что изменится в кадре, если эта переменная сдвинется?
2. **Атрибуция.** Сможет ли игрок связать это со своим действием?
3. **Дешевле ли вывести, чем посчитать?**

**Глубина ограничена сверху легибельностью, а не бюджетом.** Инструмент измерения — тест фасада в 12/12a.

## Порядок фаз (§15.1)

```
1. Затухание шока + восстановление региона   → модули 04, 06
2. Экономика: приход, затем расход            → модуль 06
3. Голод и дезертирство                       → модуль 06  ← дёргает 03!
4. Пересчёт Расход / DaysOfSupply / R P C M   → ЯДРО (публикует TF_DaysSupply)
5. Проверка правил перехода                   → модуль 07 (публикует TF_PendingArch)
6. Применение смены уклада                    → модули 07, 06
7. Дерево решений                             → модули 04, 06, 16 (веса; декремент TF_VendettaTicks)
8. Пересчёт флагов обратной связи             → модуль 09; Refresh() фасада 12
```

**Восемь фаз зафиксированы.** Модули 03 и 13 новых фаз не добавляют: работа с ростером и захват — событийные. Модуль 16 живёт внутри фазы 7 как модификатор весов. Фасад 12 дёргается в фазе 8 — аудит добавил это в таблицу явно, раньше вызов `Refresh()` из тика нигде не был прописан. **Ревизия enRAGE фаз не добавляет:** удар по складу и опознание — событийные, переезд склада — ветка фазы 7, вендетта — декремент в фазе 7, модуль 19 — событийный.

**Уточнение по фазе 3.** Дезертирство не пишет `TF_Manpower` напрямую. Оно вызывает `Roster.RemoveMany(N, причина)` в 03, который двигает строки и правит кэш дельтой. Разница не косметическая: без неё дезертирство и гибель разошлись бы в учёте, и `Steadfast` перестал бы соответствовать составу.

**Классическая ошибка:** посчитать R до списания расхода. Переход всегда отстаёт на тик, и в отладке это выглядит как «система тормозит». Двойник обязан воспроизводить эту ошибку как тест.

## Скелет

```papyrus
ScriptName CoreTickScript extends Quest

; --- модули, любой может быть None ---
Quest Property RosterModule    Auto
Quest Property ShockModule     Auto
Quest Property EconomyModule   Auto
Quest Property EvolutionModule Auto
Quest Property FeedbackModule  Auto
Quest Property FacadeModule    Auto

; --- состояние ---
GlobalVariable Property TF_Supply           Auto
GlobalVariable Property TF_RegionProsperity Auto
GlobalVariable Property TF_Control          Auto
GlobalVariable Property TF_Morale           Auto
GlobalVariable Property TF_DaysSupply       Auto  ; публикуемая производная, пишет только ядро

; --- кэши ростера: ядро их ЧИТАЕТ, но никогда не пишет ---
GlobalVariable Property TF_Manpower  Auto
GlobalVariable Property TF_Steadfast Auto

Float Property BaseUpkeep = 40.0 Auto
Float Property HeadUpkeep = 8.0  Auto

Function DoTick()
    If ShockModule     != None ; ShockModule.DecayPhase()
    EndIf                      ; EconomyModule.RegionRecoveryPhase()
    If EconomyModule   != None ; EconomyModule.IncomePhase()
    EndIf                      ; EconomyModule.UpkeepPhase()
                               ; EconomyModule.HungerPhase() → RosterModule.RemoveMany()
    RecomputeAxes()            ; читает кэши, не ростер; публикует TF_DaysSupply
    If EvolutionModule != None ; EvolutionModule.EvolutionPhase()
    EndIf
    If FeedbackModule  != None ; FeedbackModule.RefreshFlags()
    EndIf
    If FacadeModule    != None ; FacadeModule.Refresh()  — только если ячейка загружена
    EndIf
    LogTick()
EndFunction
```

Незаполненное свойство = фаза пропускается = модуль не собран.

**`RosterModule` в диспетчере есть, но не имеет фазы.** Он присутствует как свойство, чтобы другие модули могли до него дозваться, и чтобы None-guard ловил его отсутствие. Если он `None` — гибель и дезертирство не учитываются, тик при этом не падает.

Все записи в Global проходят через обёртку-логгер (11): `tick, phase, module, target, old, new, reason_code`. Записи мимо обёртки ловятся линтером в CI.

## Холостой стенд (§15.5)

Не отдельная фича, а часть ядра. Внеигровая реализация — двойник в 11.

- Прокрутить N тиков подряд без ожидания игрового времени
- Лог в CSV: тик, фаза, R, P, C, M, Archetype, Manpower, Steadfast, Supply, DaysOfSupply, RegionProsperity
- Работает с любым подмножеством модулей

Проверки: нет залипания; нет дрожания (смены реже ~10 тиков); нет вымирания раньше двух смен уклада; **кэши сходятся с ростером на каждом тике**; **набор «штопор» (11 S2e) зелёный**. Плюс обход стека правил на затенение (11).

`Debug.Notification` держать за флагом разработчика (§17.6) — **с ревизии enRAGE это Global `TF_Cfg_Dev`, по умолчанию 0.**

## Снимок состояния

**Добавлено ревизией «enRAGE».** Прецедент — enRAGE (RDR2): игрок прикладывает к баг-репорту файлы своего мира, автор загружает их у себя и видит дефект. Мы переносим идею, не транспорт.

Снимок — **полный дамп одного момента**: номер тика, версия реестра, все Global'ы реестра всех фракций, членство каждого человека в вёдрах 03, личные Global'ы именных. Формат — фиксированные строки, которые двойник (11 S4b) умеет писать и читать, а игра умеет писать.

- **Запись в игре — только отладочной командой**, не на тике: обход вёдер при снимке — событие, разрешённое правилом O(фракций).
- **Транспорт — ванильный** (`Debug.Trace` в papyrus-лог, внешний парсер). Ini или SFSE-плагин — опционально, не основание (11, правило 1).
- **Схема снимка замораживается вместе с реестром.** Добавление Global'а в реестр обязано добавить его в схему — это проверка G1.

---

## MVP ядра

**Что входит:** тик-квест с восемью фазами и None-guard'ами; реестр Global'ов с явным делением на **пять** классов; формулы `Расход`, `DaysOfSupply` (с публикацией), R и P; обёртка-логгер; стенд на 200 тиков.

**Критерий готовности:** прогон 200 тиков с заглушками отрабатывает без ошибок; лог читается; каждая запись имеет `reason_code`; **ни одной записи в кэш ростера не сделано никем, кроме 03; ни одной записи в публикуемую производную не сделано никем, кроме её вычислителя; ни одной записи в настройку не сделано симуляцией.**

**Оценка:** ~10 ч. Снимок — в бюджете 11.

## Стадии

**S1 — Часы.** Quest с 24-часовым таймером. Проверка: тик не сбивается при быстром перемещении и sleep/wait.

**S2 — Состояние.** Реестр Global'ов, ручное задание через консоль. Проверка: значения переживают сохранение/загрузку.

**S3 — Обёртка-логгер.** Единственная точка записи в Global. Проверка: линтер ловит прямой `SetValue` мимо обёртки **и запись в кэш ростера или публикуемую производную чужим модулем**.

**S4 — Производные.** `Расход`, `DaysOfSupply` + публикация, `ComputeR`/`ComputeP`. Проверка: оси не выходят за 0–100; `DaysOfSupply` не делится на ноль при пустом ростере; `TF_DaysSupply` совпадает с вычислением на каждом тике.

**S5 — Стенд.** Прогон N тиков, CSV. Проверка: 200 тиков быстрее минуты.

**S6 — Диспетчер модулей.** None-guard'ы, порядок фаз. Проверка: отключение любого модуля, включая `RosterModule`, не роняет тик.

**S6b — Снимок.** *(ревизия enRAGE)* Отладочная команда дампа, схема. Проверка: снимок из игры парсится и загружается в двойник (11 S4b).

**S7 (позже) — Среда.** Множители §13.3 из констант в настраиваемые.

## Риски

| Что | Риск | План Б |
|---|---|---|
| Деление на ноль | `Расход` = 0 при пустом ростере | `КоштБазы` > 0 всегда; проверка инвариантом |
| 24-часовой таймер | точность при sleep/fast travel не проверена | тик по накопленному игровому времени, а не по событию таймера |
| Лог в файл | доступ к ФС из Papyrus ограничен | `Debug.Trace` в papyrus-лог, парсить снаружи; либо `Papyrus Ini Manipulator` |
| Global'ы в сейве | конфликт при обновлении мода | не переименовывать после первого релиза |
| Рост числа фаз | каждая новая фаза = правка во всех модулях | восемь фаз зафиксированы |
| **Кэш разошёлся с ростером** | дельта пропущена, оси считаются по вранью | инвариант на каждом тике двойника; отладочный полный пересчёт в игре |
| **Соблазн обхода в фазе** | «тут всего триста, посчитаем честно» | архитектурный запрет; ловится профилем на 200 тиках |
| **Зеркало разошлось с вычислением** | публикуемая производная устарела (пропущена фаза) | инвариант двойника: зеркало == формула на каждом тике |
| **Префиксы второй фракции** | копипаста реестра под TF2_ разъезжается с TF1_ | реестр — таблица данных, генерируемая скриптом авторинга, не ручная копия |
| **Схема снимка отстала от реестра** *(enRAGE)* | новый Global не попал в снимок, воспроизведение молча неполное | схема генерируется из той же таблицы реестра; G1 сверяет |
| **Реестр пухнет от ревизий** *(enRAGE)* | каждая внешняя идея добавляет Global | у каждой новой строки — владелец и потребитель в момент добавления; иначе строка не добавляется (тот же критерий, что для `TF_Fragility`) |
