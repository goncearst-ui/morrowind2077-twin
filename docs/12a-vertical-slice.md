# 12a — Вертикальный срез: спецификация сборки

*Приложение к модулю 12. Рабочее задание, не дизайн.*

*Ревизия 2. Прежняя версия смешивала «движок это умеет», «это надо расставить руками» и «я это выдумал», подавая одним списком. Разделено. Ревизия «системный аудит» (2026-08-16): входы согласованы с реестром 00.*

---

## Ключ чтения

Каждая строка помечена категорией. Это единственное, что отличает спецификацию от прозы.

| | Что значит | Цена |
|---|---|---|
| **A** | Движок делает это сам: enable/disable, поворот маркера, состояние двери | минуты |
| **B** | Движок это умеет, но **каждое состояние расставляется руками** | часы на состояние |
| **C** | Не подтверждено или выдумано | **не включать, пока не проверено** |

Ошибка прежней версии была в том, что половина «упадка» была категории B, а подана как бесплатная.

---

## Принцип, которого не было

> **В движке нет «нормального состояния», от которого отклоняются.** Есть только вручную расставленные ссылки.

Следствия, определяющие весь список ниже:

1. **Сигнал существует, только если расставлены обе версии** — и норма, и отклонение.
2. **Валяющийся хлам — это состояние по умолчанию любой локации Bethesda.** «Инструмент валяется, никто не убирает» не сигнал: не убирают нигде и никогда. Чтобы это стало сигналом, нужна авторская «прибранная» версия — то есть двойная работа.
3. **Дёшевы сигналы присутствия/отсутствия** (могила есть / нет, огонь горит / нет, дверь открыта / закрыта). **Дороги сигналы качества состояния** (прибрано / запущено) — они стоят как две локации.

Весь список следов ниже перестроен на присутствие/отсутствие.

## Вычеркнуто из прежней версии

| Было | Почему убрано |
|---|---|
| «Носят ящики к кораблю» | у фракции нет корабля по умолчанию — **выдумал** |
| Анимация переноски груза | **не подтверждена** в Starfield; и не нужна (см. ниже) |
| «Кострище разворошено» | отдельный меш = арт, которого нет. Осталось: огонь горит / не горит |
| «Открытые ящики» | у контейнера нет постоянного открытого состояния — анимация транзиентна, ящик закрывается после использования |
| «Инструмент валяется» | состояние по умолчанию, не сигнал |
| «Латают ту же секцию, никакого прогресса» | сохранено, но переделано: прогресс должен быть **представим**, иначе «нет прогресса» нечитаемо |
| «Фракция строит лагерь сама, как игрок» | строительная система аванпостов из Papyrus не заводится: подтверждены только `RemoveOutpost`, `RenameOutpost`, `IsOutpost…`; функций создания/размещения модулей не найдено. **Ассеты при этом доступны в CK напрямую** |
| «Фракция выбирает место на рельефе» | рантайм-навмеш модеру недоступен; `PlaceAtMe` навмеша не создаёт. Замена — 2–3 авторские площадки, выбор между ними числовой (06) |
| Динамическое размещение объектов скриптом | рантайм-ссылки живут в сейве (распухание) и уязвимы к cell reset — SKK прямо предупреждает об этом в «Player homes anywhere». Всё расставляется заранее, переключается enable/disable |

## Проверить до сборки

Три часа, до расстановки первого актёра. Каждый пункт обрушивает часть спецификации.

| Проверка | Что рушится, если нет | План Б |
|---|---|---|
| `Enable Parent` + «Set Enable State to Opposite of Parent» в CE2 | все следы | перебор массива ссылок в `Refresh()` — дороже, но для десятка объектов терпимо |
| `cqf` в консоли Starfield | вся упряжь | дебаг-диалог у тестового NPC |
| Свойство `Ignored by Sandbox` у Idle Marker | набор «Запустение» | привязка актёров к маркерам напрямую через LinkedRef |
| Поведение объектов при **cell reset** | все следы разом | persistent-флаг; если не помогает — восстанавливать состояние из `Refresh()` при загрузке ячейки |
| Смена outfit при загрузке актёра (`SetOutfit` в Papyrus есть — вопрос в кэшировании) | ступень снаряжения | сигнал выбывает, остаются три |
| Флаг respawn у контейнеров снимается | наполненность склада | скриптовая очистка при `Refresh()` |
| **navcut при disable в CE2** — гасит ли выключенный объект свой вырез навмеша | накладка владельца с перекрытием проходов; любые будущие «состояния застройки» | все объекты-метки делать непреграждающими: знаки, флаги, разметка — но не стены |
| **Смена владельца ячейки/ссылки на фракцию** — функция записи под Starfield не найдена (на скрипте Faction её нет — проверено; кандидаты на ObjectReference/Cell не сверялись) | преступление и вторжение на захваченной площадке | владение держать своим `TF_Asset<N>_Owner`; движковое выставлять одной функцией-обёрткой, при провале — не выставлять вовсе |

*Система владения в Starfield живая: в консоли есть `IsTrespassing`, `GetTrespassWarningLevel`, `IsInMyOwnedCell`, `ModFactionRank`. Под вопросом только функция записи, не наличие системы.*

Первые два — блокирующие: без них не собрать ничего.

## Входы: семь Global'ов

| Global | Тип | Диапазон | Смысл |
|---|---|---|---|
| `TF_DaysSupply` | float | 0–40 | на сколько суток хватит. **Зеркало производной из реестра 00** — в тесте задаётся напрямую, в рабочем режиме публикует ядро |
| `TF_Manpower` | short | 0–10 | сколько живо **в кадре среза.** В рабочем режиме — не сырой кэш ростера, а ступень от него (маппинг N → 0–10 в `Refresh()`): сцена показывает до 10 человек при любом ростере |
| `TF_Shock` | short | 0–100 | свежесть удара. **Локальный синоним `TF_PersonnelShock`** — в рабочем режиме читается он; отдельного Global не заводить |
| `TF_Archetype` | short | 0–3 | канонический enum 00: 0 Хранители, 1 Хищники, 2 Контролёры, 3 Дрейфующие |
| `TF_PendingArch` | short | −1…3 | −1 = перехода нет. **Зеркало из 07 (реестр 00)** |
| `TF_DayVariant` | short | 0–2 | ротация обычного дня; в рабочем режиме пишет ядро (`день % 3`) |
| `TF_AssetOwner` | short | 0–2 | кто держит площадку. Локальный синоним `TF_Asset<N>_Owner` этой площадки |

**Выходы:** `TF_SceneSet` (short 0–5), `TF_RepairStage` (short 0–4) — считаются, не задаются.

`TF_DaysSupply` как прямой вход принципиален: фасад потребляет **производную**, а не сырой запас. При подключении к тику меняется только источник — теперь это зафиксировано и в 00 (класс «публикуемая производная»).

## Стек наборов

Приоритет живёт в одной функции, пакеты проверяют равенство. Тот же паттерн, что стек правил в 07.

```papyrus
Function ComputeSceneSet()
    Int s = 0
    If TF_Manpower.GetValue() <= 3
        s = 5                                 ; Запустение
    ElseIf TF_Shock.GetValue() >= 60
        s = 3                                 ; Сжатие
    ElseIf TF_PendingArch.GetValue() >= 0
        s = 4                                 ; Сборы
    ElseIf TF_Archetype.GetValue() == 3
        s = 5                                 ; Запустение
    ElseIf TF_DaysSupply.GetValue() < 10.0
        s = 2                                 ; Скудный день
    Else
        s = TF_DayVariant.GetValue()          ; 0/1/2
    EndIf
    TF_SceneSet.SetValue(s)
EndFunction
```

Порядок «Сжатие выше Сборов» даёт читаемую последовательность: удар → сжались → шок спал, окно ещё идёт → собираются → сменились. Три кадра за пять суток.

## Наборы сцен

Ростер: **10 актёров** — вожак, квартирмейстер, техник, 5 бойцов, 2 работяги.
Реализация: Quest с алиасами, пакеты на алиасах (перекрывают собственный список актёра), условие `GetGlobalValue TF_SceneSet == N`. **Категория B целиком** — каждый набор это отдельная расстановка маркеров.

### 0/1/2 — Обычный день, три варианта

Различаются **центром тяжести и числом людей в зоне**, не анимациями. Те же позы в другом углу не читаются как другой день.

| | Вариант 0 | Вариант 1 | Вариант 2 |
|---|---|---|---|
| Центр тяжести | периметр | склад | ангар |
| Вожак | обход | у терминала | отсутствует |
| Квартирмейстер | у склада | у склада, дверь открыта | в ангаре |
| Техник | на крыше | на крыше | в ангаре, маркер сварки |
| Бойцы 5 | 2 периметр, 1 пост, 2 костёр | 4 у склада, 1 пост | 2 сидят, 3 костёр |
| Работяги 2 | у периметра | у склада | у костра |

Идёт по `TF_DayVariant`, в рабочем режиме `день % 3`.

*Маркеры ремонта, сварки, работы за верстаком в Starfield ванильные — это невидимая «мебель», которой NPC уже пользуются в игре. Конкретные EditorID искать в Object Window, не выдумывать.*

### 2 — Скудный день (`DaysSupply < 10`)

Сигнал не в «грустных анимациях», а в **отсутствии нового и в остановившемся ремонте**.

| Элемент | Кат. |
|---|---|
| `TF_RepairStage` не растёт (см. ниже) | A |
| 4 человека на маркерах без задачи вместо работы | B |
| Огонь горит, котёл выключен/отсутствует | A |
| Дверь склада открыта, контейнеры пусты | A |
| 1 пост вместо двух — один боец выключен с постового маркера | A |

### 3 — Сжатие (`Shock >= 60`)

| Элемент | Кат. |
|---|---|
| Все внутри периметра: наружные маркеры не используются | B |
| 4 на постах лицом наружу, разнесены по секторам | B |
| 3 сидят рядом на маркерах чистки оружия | B |
| Огонь не горит | A |
| Вожак у входа, маркер с поворотом | A |

### 4 — Сборы (`PendingArch >= 0`)

Самый громкий кадр в моде: это окно вмешательства игрока (dwell time, 07).

**Перенос показывается результатом, а не процессом.** Между посещениями ящики убыли со склада и появились у ворот. Игрок достраивает транспортировку сам — это дешевле, честнее и не зависит от неподтверждённой анимации.

| Элемент | Кат. |
|---|---|
| Штабель у ворот включён, штабель у склада выключен | A |
| Контейнеры склада опустошены скриптом | A |
| Техник **снимает** оборудование: маркер снят, панель-заглушка включена | B |
| 1 боец уходит по дороге (travel package к дальнему маркеру) | B |
| Вожак и квартирмейстер стоят у терминала, не работают | B |
| Огонь не горит | A |

### 5 — Запустение (`Archetype == 3` или `Manpower <= 3`)

Перестроен целиком на присутствие/отсутствие.

| Элемент | Кат. |
|---|---|
| 5–6 актёров на **разнесённых** маркерах с `Ignored by Sandbox`, привязка адресная | B |
| Idle-чатер отключён условием на квесте диалогов — «не разговаривают» это условие, а не свойство пакета | A |
| Постовых актёров нет: выключены | A |
| Огонь не горит | A |
| Дверь склада открыта, контейнеры пусты | A |
| Вожак отсутствует на обычном маркере, включён на отдельном с поворотом спиной | A |
| Могилы: включено максимальное число | A |
| `TF_RepairStage` откатился до 0 | A |

## Склад: настоящие контейнеры, не декорация

Главная содержательная правка ревизии.

Декоративная наполненность — ложь, которую игрок обнаружит при первом подходе. Кладовая приглашает к взаимодействию сильнее, чем фоновый штабель, и молчащий сундук ломает доверие ко всему остальному.

**Решение:** 4–6 настоящих контейнеров, содержимое которых `Refresh()` приводит в соответствие с `TF_DaysSupply`.

| `TF_DaysSupply` | Содержимое | Штабель-статик у склада |
|---|---|---|
| ≥ 15 | полные пайки, запчасти | включён |
| 5–15 | остатки, вскрытые упаковки | выключен |
| < 5 | пусто | выключен |

Что это даёт сверх картинки:

- видимое и лутаемое — **один объект**, врать нечем
- кража еды у голодающих становится возможной и адресной — это буквально 06 S7 (`OnItemRemoved`, форсированный пересчёт)
- игрок получает способ **ухудшить** положение клана точечно, а не только украсть абстрактный запас

**Обязательно:** снять флаг respawn. Иначе содержимое регенерирует при сбросе ячейки, и вся конструкция обнуляется.

## Следы

Каждая группа — master-маркер, дети на `Enable Parent`.

| Группа | Кат. | Управляется | Ступени |
|---|---|---|---|
| `TF_Trace_Graves` | A | `TF_Manpower` | 10−N могил, по одной |
| `TF_Trace_CratesFull` | A | `TF_DaysSupply` | вкл при ≥ 15 |
| `TF_Trace_CratesGate` | A | `TF_SceneSet == 4` | штабель у ворот при сборах |
| `TF_Trace_BunksEmpty` | A | `TF_Manpower` | вкл при ≤ 7 |
| `TF_Trace_Wreck` | A | вручную | потерянный аванпост |
| `TF_Door_Storeroom` | A | `TF_DaysSupply` | открыта при < 10 |
| `TF_Fire_Main` | A | `TF_SceneSet` | не горит при 3, 4, 5 |
| `TF_Mark_Owner0..2` | A | `TF_AssetOwner` | знаки/флаги/разметка, ровно одна группа включена |
| `TF_Trace_Sacked` | A | ставится модулем 13 | следы штурма: обгорелые пятна, разбитая дверь, брошенное оружие |

Убраны: «сварные заплаты» (заменены прогрессом ремонта), «брошенный пост» (дублирует выключенных постовых), «инструмент» (не сигнал).

### Накладка владельца — три группы, одна включена

Единственный сигнал, который читается **до встречи с людьми**. Категория A целиком.

```papyrus
Function RefreshOwnerMarks()
    Int o = TF_AssetOwner.GetValue() as Int
    MarkOwner0.Enable(o == 0)   ; фактически: Enable/Disable по индексу
    MarkOwner1.Enable(o == 1)
    MarkOwner2.Enable(o == 2)
EndFunction
```

Требования к содержимому групп:

- **Только непреграждающие объекты** — знаки, флаги, разметка, граффити, тряпки на ограде. Никаких стен и створок: пока navcut при disable не проверен (см. «Проверить до сборки»), перекрывать проходы нельзя.
- **Различимо силуэтом и цветом издали**, не деталью. Тот же критерий, что у стадий ремонта.
- **Три группы — потолок.** Больше владельцев в прототипе не бывает.

### `TF_Trace_Sacked` — кадр сразу после штурма

Включается модулем 13 при смене владельца, гасится вручную/по восстановлению `TF_RepairStage`.

Переиспользуется дважды, и в этом весь смысл: это **и** «здесь только что был бой», **и** «здесь недавно были другие». Одна расстановка, два сообщения.

**Что сюда не входит:** отдельные состояния «разграблено» для каждого владельца. Состояние — общий слой, владелец — накладка. Перемножение запрещено (12).

---

### Прогресс ремонта — единственный след с памятью

`TF_RepairStage` 0–4, недостроенная секция периметра, **5 заранее собранных состояний** (категория B, самая дорогая позиция в списке).

```
DaysSupply >= 15  → стадия +1 (потолок 4)
DaysSupply 10–15  → без изменений
DaysSupply < 10   → стадия −1, не чаще раза в 3 тика
```

**Информация не в прогрессе, а в его остановке.** Вернувшись через неделю, игрок читает три разных сообщения: продвинулись, стоит, откатилось.

Это единственный объект, дающий **контраст во времени** — то, что иначе требует второй фракции. Ради этого он и стоит своей цены.

Требования: разница между стадиями должна читаться **силуэтом**, а не деталью. Потолок обязателен, иначе через полгода локация превращается в крепость и мод молча становится про застройку.

## Скрипт-упряжь

Остаётся после подключения к тику — меняется только вызывающий.

```papyrus
Function Refresh()
    ComputeSceneSet()
    UpdateRepairStage()
    RefreshTraces()        ; enable/disable групп по порогам
    RefreshOwnerMarks()    ; накладка владельца по TF_AssetOwner
    RefreshContainers()    ; содержимое склада по TF_DaysSupply
    RefreshOutfits()       ; ступень снаряжения
    RefreshActors()        ; EvaluatePackage() на загруженных
EndFunction
```

Ступени снаряжения (совпадают с 01 S5): ≥ 15 — `TF_Outfit_Good`; 5–15 — `TF_Outfit_Worn`; < 5 — `TF_Outfit_Rags`.

## Протокол теста

1. **Установку делает не автор.** Другой человек выбирает 4 расклада из 6 и записывает в файл. Или скрипт со случайным сидом пишет в файл, который не открывается до конца чтения.
2. **Пауза ≥ 7 дней.** В расписании PI встроена между И2 и И4.
3. **Чтение:** прилететь, 60 секунд, без диалогов, консоли и логов.
4. **Ответы записываются до сверки:**

| # | Вопрос | Варианты |
|---|---|---|
| 1 | Сколько их и было ли больше? | столько же / убыло немного / убыло сильно |

### Урезанный вариант — 15 ч

Если 27 ч неприемлемо, режется так, чтобы тест остался валидным:

- два варианта обычного дня вместо трёх (−1.5)

## Что этот срез не проверяет

- **Правильность симуляции** — состояние задаётся руками
- **Производительность тика** — тика нет
- **Интересность геймплея** — игроку нечего делать
- **Долгосрочную читаемость** — расклады статичны, изменение во времени даёт только прогресс ремонта

Срез отвечает ровно на один вопрос: **если состояние клана известно, видно ли его глазами.**
